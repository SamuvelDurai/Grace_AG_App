CHURCH CONNECT COMPLETE ANDROID APP DEVELOPMENT SPECIFICATION Version:
1.0 Purpose: Master project brief to provide to Google AI Studio

============================================================ 1. PROJECT
OVERVIEW ============================================================

Build a production-minded native Android application named “Church
Connect”.

Tagline: “Growing in Faith. Connected as One Family.”

Church Connect is a bilingual church management and believer engagement
platform. It connects church members (believers), pastors, and super
administrators through one Android application with role-based
dashboards and permissions.

The app must be designed for Android Studio development. Use native
Android technologies: - Kotlin - Jetpack Compose for UI - Material 3 -
Navigation Compose - MVVM architecture - Kotlin Coroutines and Flow -
Repository pattern - Hilt for dependency injection (if supported by the
project setup) - Firebase Authentication - Cloud Firestore - Firebase
Storage - Firebase Cloud Functions for trusted server-side operations -
Firebase Cloud Messaging for push notifications - Firebase Crashlytics
and Analytics, with appropriate consent and privacy controls

Do not build a web app or Flutter app. This is a native Android Studio
project.

Initial launch is for one church. However, design the data model with a
churchId field and tenant-aware repositories/security rules so that
multiple churches can be supported in a future release without
rebuilding the whole system.

The app must support: - Tamil (ta) - English (en) - User-selectable
language - Language persistence between sessions - All user-facing text
through Android string resources; do not hardcode UI text in
composables. - Proper Tamil font rendering and layouts.

IMPORTANT IMPLEMENTATION APPROACH: Build the application in small,
compilable phases. Do not generate the entire project as one huge code
response. First create the project architecture and foundational
screens, then implement each feature module. Keep the app runnable after
every phase. Provide complete file paths and complete file contents for
every new or modified file. Do not use pseudocode, TODO placeholders for
core functionality, fake payment success, or buttons that do nothing. If
an external service requires credentials, clearly mark the configuration
step and provide a safe test-mode implementation.

============================================================ 2. USER
ROLES AND ACCESS CONTROL
============================================================

There are three roles:

A. BELIEVER - Can register or sign in. - Can submit a church membership
application. - Can edit permitted personal profile fields. - Can view
their own membership details and membership card. - Can view daily Bible
verses, announcements, sermons, events and church content. - Can submit
private prayer requests. - Can request pastoral counselling
appointments. - Can view their own subscription dues, payments,
offerings and receipts. - Can view their own attendance history if the
church enables this feature. - Can submit testimonies for pastor
approval. - Cannot view other believers’ private profiles, payment
details, prayer requests or counselling records. - Cannot approve their
own membership or change their role.

B. PASTOR - Can sign in only after a Super Admin has created or approved
the pastor account. - Can manage believers belonging to the assigned
church. - Can review and approve/reject membership applications. - Can
create and publish announcements in Tamil and English. - Can publish
daily Bible verses and devotionals. - Can manage events, sermons,
attendance, baptism records and ministry groups. - Can view and respond
to prayer requests according to privacy settings. - Can manage
counselling appointments. - Can review and approve testimonies. - Can
view subscription and offering reports only if the Super Admin grants
finance permission. - Cannot create or promote another Super Admin. -
Cannot access data belonging to another church. - Important actions must
be recorded in audit logs.

C. SUPER ADMIN - Highest application-level authority. - Can create,
approve, suspend and manage pastor accounts. - Can manage believers and
membership records. - Can configure church name, logo, address, contact
details, service timings and settings. - Can configure subscription
amounts, due dates and payment options. - Can manage permissions for
pastors and authorized staff. - Can manage content, notifications,
reports and system settings. - Can access financial reports and
reconcile transactions. - Can view audit logs. - Can manage account
status and data export requests. - Can configure the app’s
church-specific content. - Must be protected from public
self-registration. Initial Super Admin must be provisioned securely by
the developer using Firebase Admin SDK or a trusted server-side process.

SECURITY RULE: Never trust a role value supplied by the Android client.
Store role and church assignment in protected Firestore documents and/or
Firebase custom claims. Only trusted server-side code may grant or
change privileged roles. Firestore and Storage Security Rules must
enforce access independently of the UI.

Use least-privilege permissions. A pastor’s permissions should be
configurable, especially for financial records, counselling and
sensitive member information.

============================================================ 3.
AUTHENTICATION AND ONBOARDING
============================================================

Create the following screens: 1. Splash screen with Church Connect logo.
2. Welcome/onboarding screen. 3. Language selection: தமிழ் / English. 4.
Sign-in screen using phone number and Firebase Phone Authentication OTP.
5. OTP verification screen. 6. New believer registration form. 7.
Membership application submitted screen. 8. Pending approval screen. 9.
Account suspended/disabled screen. 10. Role-based dashboard routing.

Registration fields: - Full name - Phone number (verified through OTP) -
Email (optional) - Date of birth (optional) - Gender (optional; only
collect if church needs it) - Address (optional) - Profile photo
(optional) - Church/membership selection if applicable - Consent to
privacy notice and terms

Do not require unnecessary sensitive information during initial
registration. Collect extended church profile information after
registration and explain why it is needed.

Believer registration workflow: 1. User enters phone number. 2. Firebase
sends OTP. 3. User verifies OTP. 4. User completes basic registration.
5. Create a membership application with status PENDING. 6. Pastor or
authorized admin reviews the application. 7. If approved, assign a
unique membership ID, for example CC-00001. 8. Activate believer account
and show the believer dashboard. 9. If rejected, show a respectful
status and allow correction/resubmission if enabled.

Do not allow an unverified user to access member-only content or other
members’ records.

APP FEATURES
============================================================

4.1 BELIEVER HOME DASHBOARD

Use a clean, welcoming and peaceful design. Avoid overcrowding the home
screen.

4.2 PERSONAL PROFILE AND CHURCH MEMBERSHIP

Profile fields: - Unique membership ID - Profile photo - Full name -
Date of birth - Gender (optional) - Phone number - Email (optional) -
Address - Emergency contact (optional, only if needed) - Father’s name
(optional) - Mother’s name (optional) - Spouse name (optional) -
Children/dependants (optional) - Church joining date - Membership
status - Baptism status - Baptism date - Baptism location - Baptized by
/ pastor name - Ministry or fellowship group - Profile verification
status

Features: - View and edit permitted fields. - Request changes to
verified fields. - Upload profile picture. - Upload baptism certificate
(optional). - View membership history. - View digital membership card
with QR code. - Download/share membership card only if enabled by
church.

The QR code must contain a random membership identifier or secure
verification token, not private personal details. QR scans must not
expose full profiles to unauthenticated users.

4.3 DAILY BIBLE VERSE AND DEVOTIONAL

Features: - Verse of the day. - Bible book, chapter and verse
reference. - Tamil and English display. - Short devotional/reflection. -
Save favourite verses. - Share verse as text or image. - Browse previous
verses. - Optional daily reminder notification. - Admin/pastor content
publishing.

Copyright requirement: Use public-domain Bible translations or
translations for which the church has the required license. Do not
scrape or reproduce copyrighted Bible translations without permission.
Store translation/source metadata for each verse. Allow the church to
configure approved translations.

4.4 ANNOUNCEMENTS

Believers can: - View announcements. - Filter by category. - View
attached image, poster or PDF. - See publish date and expiry date. -
Receive push notifications. - View Tamil or English content. - Mark an
announcement as read.

Announcement categories: - Sunday service - Prayer meeting - Fasting
prayer - Youth meeting - Women’s fellowship - Men’s fellowship -
Children’s ministry - Special events - General notice - Emergency notice

4.5 MONTHLY SUBSCRIPTIONS

This is a church-configured monthly contribution/dues module. Do not
assume all churches require mandatory subscriptions.

Features: - Admin-configurable monthly amount. - Different amount rules
if the church authorizes them. - Due date and grace period. - Monthly
payment status. - Paid, pending, overdue, waived and partially paid
states. - Payment history. - Online payment option. - Cash/manual
payment entry by authorized finance staff. - Receipt generation. -
Payment reminder notifications. - Exemption/waiver with reason and audit
record. - Partial payment support if enabled. - Member can view only
their own records.

Important distinction: Monthly subscriptions/dues and voluntary
offerings/donations must be separate modules and separate accounting
records.

Payment safety: - Integrate a supported payment gateway such as Razorpay
only after merchant account setup. - Use gateway test mode during
development. - Create payment orders on a trusted backend/Cloud
Function. - Verify gateway signatures and payment status on the
backend. - Never mark a payment paid based only on a client callback or
screenshot. - Use idempotency/unique transaction IDs to prevent
duplicate records. - Store gateway references, amount, currency, status,
timestamps and receipt reference. - Do not store card numbers, UPI PINs
or banking passwords. - Provide clear failed/pending/success states. -
Refunds and reversals must be recorded and auditable.

4.6 OFFERINGS AND DONATIONS

Separate categories: - General offering - Tithe - Special offering -
Missionary support - Church building fund - Charity/welfare - Other
church-approved category

Believer features: - Select category. - Enter amount. - Add optional
note. - Pay online or follow church-approved offline process. - View own
offering history. - Download receipt. - View donation campaign details.

Admin features: - Create and manage donation categories/campaigns. -
View authorized collection reports. - Record cash/offline donations. -
Reconcile online payments. - Export reports. - Maintain audit records.

Do not display public donor lists or amounts without explicit consent.

4.7 PRAYER REQUESTS

Believers can: - Submit prayer title and description. - Select privacy:
pastor-only, authorized prayer team, or share with congregation (only if
enabled and explicitly consented). - Choose whether their name is
displayed. - View their own request status. - Receive a private response
or encouragement. - Withdraw/delete a request where policy permits.

Pastor can: - View requests they are authorized to access. - Assign a
request to an authorized prayer team member. - Add private pastoral
notes. - Respond to the believer. - Update status: New, In Review,
Prayed For, Responded, Closed.

Never expose private prayer requests in general announcements or public
notifications. Notifications should avoid revealing sensitive content on
a lock screen.

4.8 SERMONS AND MEDIA

-   Sermon title and description.
-   Speaker/pastor.
-   Date.
-   Bible passage/reference.

-   Favourite/save sermon.

-   Share sermon link.

-   Date and start/end time.

-   Poster/image.

-   Pastor/authorized staff can record attendance for services and

-   Support manual attendance and QR check-in.
-   QR check-in must use a time-limited or event-specific token to

-   Prevent duplicate attendance entries.

============================================================ 9.
TECHNICAL ARCHITECTURE
============================================================

Use a clean, modular MVVM architecture.

Recommended layers:

PRESENTATION: - Jetpack Compose screens - Reusable UI components -
Navigation - ViewModels - UI state classes - Localization

DOMAIN: - Use cases/business rules - Domain models - Repository
interfaces - Role/permission rules

DATA: - Repository implementations - Firestore data sources - Firebase
Auth data source - Firebase Storage data source - Cloud Functions
client - DTO-to-domain mapping - Offline/cache handling where
appropriate

CORE: - Dependency injection - Theme - Localization - Logging - Error
handling - Network status - Security/session utilities

Suggested package structure:

com.churchconnect app/ MainActivity.kt ChurchConnectApp.kt
AppNavigation.kt core/ common/ design/ localization/ network/ security/
util/ data/ auth/ firestore/ storage/ repositories/ models/ domain/
model/ repository/ usecase/ feature/ onboarding/ authentication/
believer/ profile/ bible/ announcements/ subscriptions/ offerings/
prayer/ sermons/ events/ attendance/ baptism/ counselling/ testimonies/
pastor/ superadmin/ notifications/ settings/ di/ MainApplication.kt

Use feature-based packages. Keep ViewModels focused and do not put
Firestore calls directly inside Composable functions.

Use: - StateFlow for screen state. - Kotlin Coroutines for asynchronous
work. - Repository interfaces for testability. - Sealed classes/data
classes for loading, success and error states. - Navigation arguments
using stable IDs, not full private user objects. - Centralized error
mapping. - Unit tests for business logic and permission rules.

============================================================ 11.
SECURITY, PRIVACY AND COMPLIANCE
============================================================

Security is a core requirement, not a final polish task.

Implement: - Firebase Authentication. - Firestore Security Rules. -
Firebase Storage Security Rules. - Trusted Cloud Functions for
privileged operations. - Role and church assignment validation. -
Least-privilege access. - Input validation on client and server. - App
Check where supported. - Secure handling of OTP and sessions. - Audit
logs for sensitive actions. - Regular backup and restore testing. -
Secure secrets management. - No API secret keys inside the Android
APK. - No public read access to member records. - No public access to
private prayer/counselling records. - No unrestricted access to
financial records.

Data privacy: - Show a privacy notice before collecting personal data. -
Collect only information needed by the church. - Explain why optional
family and spiritual details are requested. - Obtain appropriate
consent. - Provide a way to request correction or deletion, subject to
lawful retention requirements. - Define retention periods for financial,
membership and counselling records. - Restrict exports and log who
performs them. - Do not log OTPs, passwords, full phone numbers, private
prayer text or payment secrets. - Follow applicable Indian data
protection requirements, including the Digital Personal Data Protection
framework and rules in force at deployment.

Create test cases proving: 1. Believer A cannot read Believer B’s
private profile. 2. Believer cannot change their own role. 3. Believer
cannot approve their own membership. 4. Pastor cannot access another
church’s records. 5. Pastor without finance permission cannot read
financial collections. 6. Private prayer requests are visible only to
authorized recipients. 7. Client cannot mark a payment as successful. 8.
Unauthenticated users cannot read private records. 9. Suspended accounts
cannot access protected features. 10. Super Admin role cannot be granted
from the client.

============================================================ 12. PAYMENT
AND FINANCE DESIGN
============================================================

Use Razorpay or another approved payment gateway after the church has a
verified merchant account.

Development sequence: 1. Implement payment data models. 2. Implement
payment status UI with test data clearly labelled. 3. Create a trusted
backend order-creation function. 4. Launch gateway checkout in test
mode. 5. Verify gateway signature on the backend. 6. Process verified
webhooks. 7. Update payment and subscription records
transactionally/idempotently. 8. Generate receipts only after verified
success. 9. Test success, failure, cancellation, pending and duplicate
webhook cases. 10. Switch to live mode only after merchant approval and
end-to-end testing.

Do not promise automatic recurring debits unless the gateway, merchant
account and required customer authorization support them. A monthly due
reminder and a recurring auto-debit are different features.

Financial reports: - Daily collections. - Monthly subscription
collections. - Offering category totals. - Cash versus online. - Pending
and failed transactions. - Refunds/reversals. - Member-wise history for
authorized finance users. - Downloadable CSV/PDF reports.

Use INR as the default currency, but make currency a church
configuration.

DEVELOPMENT PHASES AND ACCEPTANCE CRITERIA
============================================================

PHASE 1: FOUNDATION Build: - Android Studio Kotlin project. - Jetpack
Compose and Material 3. - App theme and reusable components. -
Tamil/English localization. - Firebase project connection. -
Authentication. - Role-based navigation.

Acceptance: - App builds and runs. - User can select language. - OTP
authentication works in configured test environment. - User is routed to
the correct role dashboard. - Unapproved users cannot enter the believer
dashboard.

PHASE 2: BELIEVER PROFILE Build: - Registration and membership
application. - Profile photo upload. - Personal and church details. -
Baptism details. - Membership ID and QR card.

Acceptance: - Member can submit an application. - Pastor can approve
it. - Approved member receives a unique ID. - Member can only access
permitted personal data.

PHASE 3: CHURCH CONTENT Build: - Daily Bible verse. - Announcements. -
Events. - Sermons. - Notifications.

Acceptance: - Pastor can publish content. - Believers can view content
in Tamil and English. - Push notifications reach intended users. -
Expired announcements are handled correctly.

PHASE 4: FINANCE Build: - Monthly dues. - Offerings. - Payment gateway
sandbox. - Receipts. - Finance reports.

Acceptance: - Client cannot fake payment success. - Verified payments
update records once. - Member sees only their own history. -
Unauthorized pastor cannot access financial data.

PHASE 5: PASTOR MANAGEMENT Build: - Member search and filters. - Baptism
register. - Attendance. - Prayer requests. - Counselling. -
Ministries. - Reports.

Acceptance: - Pastor can manage assigned church records. - Sensitive
data remains restricted. - Important changes are audited.

PHASE 6: SUPER ADMIN Build: - Pastor management. - Permission
management. - Church configuration. - Audit logs. - Financial
configuration. - Backup/status screens.

Acceptance: - Only provisioned Super Admin can access this dashboard. -
Role changes happen through trusted backend logic. - Administrative
actions are logged.

PHASE 7: ADVANCED FEATURES Build: - Testimonies. - Bible study plans. -
Live service integration. - Advanced notifications. - Optional AI Bible
assistant.

Acceptance: - All advanced features respect content licensing, privacy
and access rules.

PHASE 8: RELEASE - Full regression testing. - Security rules review. -
Performance optimization. - Privacy policy. - App icon and
screenshots. - Signed Android App Bundle. - Internal testing track. -
Production release after church approval.

============================================================ 18. FINAL
PRODUCT GOAL
============================================================

Church Connect should become a secure, reliable and easy-to-use digital
platform for church life.

Believers should be able to: - Stay connected with their church. - Read
daily Bible verses. - Receive announcements. - Maintain their membership
profile. - View baptism and church records. - Manage subscriptions and
offerings. - Submit prayer requests. - Watch sermons and join events.

Pastors should be able to: - Manage believers. - Publish church
content. - Maintain church records. - Organize events and attendance. -
Support believers through prayer and counselling. - Access authorized
financial reports.

Super Admin should be able to: - Manage pastors and permissions. -
Configure the church. - Control system settings. - Monitor financial and
administrative operations. - Maintain security and accountability.

Build for trust, privacy, clarity, accessibility and long-term
maintainability.
